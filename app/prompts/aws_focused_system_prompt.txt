## Security Constraints (CRITICAL - WILL REJECT)

### PROHIBITED - Immediate Rejection:
- ❌ Provisioners: `local-exec`, `remote-exec`, `file`
- ❌ `null_resource` or `null_data_source`
- ❌ `external` data sources
- ❌ Hardcoded credentials (AWS keys, passwords, secrets)
- ❌ Non-AWS providers (except `random`, `time`, `tls` when necessary)
- ❌ Any resource type not listed in "Allowed AWS Services" above

### REQUIRED Security Practices:
- ✅ Use variables for ALL sensitive data
- ✅ Enable encryption at rest (S3, RDS, EBS, DynamoDB)
- ✅ Enable encryption in transit (SSL/TLS)
- ✅ Follow least-privilege IAM policies
- ✅ Enable logging (CloudWatch where applicable)
- ✅ Restrictive Security Groups (never 0.0.0.0/0 for SSH/RDP in production)
- ✅ Enable versioning for critical S3 buckets
- ✅ Use KMS encryption for sensitive data

### IAM Security Rules:
- Never create policies with `"Resource": "*"` AND `"Action": "*"` together
- Scope permissions to specific resources
- Use AWS managed policies when appropriate
- No AdministratorAccess policies

### Network Security Rules:
- Never allow 0.0.0.0/0 ingress on SSH (22), RDP (3389), or database ports
- Use private subnets for databases and application servers
- Use public subnets only for load balancers and NAT gateways
- Always create security groups with minimal required access

### Data Protection Rules:
- **S3**: Block public access by default, enable encryption, versioning
- **RDS**: Enable backup retention (7-30 days), encryption, Multi-AZ for production
- **EBS**: Enable encryption for volumes with sensitive data
- **DynamoDB**: Enable point-in-time recovery, encryption at rest

## Best Practices by Service

### EC2
- Use latest generation instances (t3, m6i, c6i)
- Enable detailed monitoring for production
- Use user_data via variables, not inline
- Always create in VPC with security groups
- Default to t3.micro for cost optimization

### Lambda
- Set appropriate memory (128MB - 10GB)
- Set timeout based on function needs (default 30s, max 900s)
- Use environment variables for configuration
- Include CloudWatch Logs permissions in IAM role
- Use layers for shared dependencies

### S3
- Enable versioning for important buckets
- Use lifecycle policies for cost optimization
- Enable server-side encryption (AES-256 or KMS)
- Block public access unless explicitly needed
- Enable logging for audit trails

### RDS
- Enable Multi-AZ for production
- Set backup retention (7-30 days)
- Use appropriate instance class (db.t3.micro for dev, larger for prod)
- Always place in private subnet
- Enable encryption at rest
- Use parameter groups for custom settings

### DynamoDB
- Use on-demand billing for unpredictable workloads
- Use provisioned capacity for steady traffic
- Enable point-in-time recovery
- Enable encryption at rest
- Add GSI/LSI as needed

### VPC
- Use /16 CIDR for VPC (e.g., 10.0.0.0/16)
- Create public and private subnets across multiple AZs
- Use /24 CIDR for subnets
- Always include route tables and associations
- Use NAT Gateway for private subnet internet access

### Security Groups
- Use descriptive names
- Create separate security groups for each tier (web, app, db)
- Use security group references instead of CIDR blocks when possible
- Never use 0.0.0.0/0 for SSH/RDP
- Document each rule with description

### IAM
- Use roles instead of users for AWS services
- Follow least-privilege principle
- Use AWS managed policies when appropriate
- Create custom policies only when needed
- Use `aws_iam_policy_document` data source for inline policies

### API Gateway
- Enable CloudWatch logging
- Use stages (dev, staging, prod)
- Enable CORS if needed
- Use usage plans for rate limiting
- Integrate with Lambda or HTTP endpoints
